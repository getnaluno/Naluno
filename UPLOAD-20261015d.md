## "Couldn't enable notifications" (and calls not ringing)
Cause, reproduced on 15b: since 14 Oct a phone's push address may only be
kept in its private vault (the public profile only allows removing it).
The vault code looked for the database at `window.fbDb`, but the app keeps
it in a script variable that is not on `window`. So the vault never saw the
database, nothing was ever written to it, the app fell back to writing the
public profile, the rules refused that, and you got "Couldn't enable
notifications". Any phone whose address changed since 14 Oct (signing out
and in, a reinstall) could no longer be rung. The vault code was the same
before 14 Oct; it just never mattered until then.

Fix (d): the vault reads the app's own database and user. Tested on 15b
vs 15d with the 14 Oct rule emulated: 15b "Couldn't enable notifications",
nothing saved; 15d "Call notifications enabled", address in the vault, none
on the public profile; after signing out and back in it saves itself again.

Side effect, now working for the first time: the Compass lock password,
the recovery email and the message-key backup are also saved in the vault
(they silently were not). Copying older values from the public profile into
the vault now runs too, but only copies: it never deletes anything from the
public profile, never overwrites a value already in the vault, waits until
the vault has been read, and never touches the console password. The
console does not load this file.

## Empty feed after signing out and back in
Reproduced on 15b: when the public feed's live read failed once (a refusal
while the sign-in settles, or the index missing or still being built), the
app tried one fallback that needs an index that does not exist, then stayed
on "No permanent Broadcasts yet" for the rest of the session. A normal
reopen hid this behind the copy of the feed kept on the phone; signing out
removes that copy, which is why the empty screen showed up then.

Fix (d): any failure is kept and the feed asks again (2 s, 4 s, 8 s …, then
every minute while signed in); an error from an old listener can no longer
stop the new one; and the empty screen says what happened instead of "No
permanent Broadcasts yet". When the database says an index is missing, the
screen shows its link to build it. Tested: two refusals right after
sign-in: 15b empty for good, 15d 20 of 20 at once; index missing then
built: 15b empty for good, 15d shows the reason with the link, then the
feed once the index exists.

## Why the feed needs that index (your question)
On 10 Oct the database rules started enforcing private and scheduled
Broadcasts: anyone may list a Broadcast only if it is listed, not hidden,
not held, visibility "public" and its publishAt has passed. The database
does not filter for the rules; it refuses any question that could return
something not allowed. So the feed must ask exactly that question
(listed = true, hidden = false, held = false, visibility = "public",
publishAt ≤ now, newest first), and Firestore can only answer a question
of that shape with a composite index on those five fields. Without it, the
feed cannot load at all. Removing visibility from the query would make the
rules refuse it, and loosening the rules would let anyone read private
posts, so the index has to stay.

Please check it in Firebase console → Firestore Database → Indexes →
Composite:
- Collection `broadcasts`: listed ↑, hidden ↑, held ↑, visibility ↑,
  publishAt ↓, query scope Collection, status Enabled.
- Collection `broadcasts`: creatorUid ↑, listed ↑, hidden ↑, held ↑,
  visibility ↑, publishAt ↓ (a creator's channel).
- Collection `signals`: public ↑, hidden ↑, held ↑, expiresAt ↓.
If one is missing or still building, the app now says so on the empty
feed with the database's own link.
