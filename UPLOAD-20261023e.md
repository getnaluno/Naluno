# Build 20261023e — upload

Calls connect faster, a phone never falls back to an older version once a
newer one has landed (app and console), and the Callsign dial gets its
settings back. Includes everything that differs from GitHub's current build
(23b), so it also carries all of 23c/23d. If 23d is not uploaded yet, upload
this instead.

## 1. Why calls took long to connect, and what changed
Measured with two phones over a mobile-network relay, timing taken inside the
page (not from outside).

**What was slow**
- **Answering a video call.** While it rang, the answering phone first waited
  for its own camera (about 1 s on a phone) and the filters (up to 0.6 s)
  before it built the connection. The connection that should be ready by
  Answer usually wasn't, so it was built after Answer: 2–2.7 s of silence,
  about 3 s before the picture.
- **Starting a call.** The caller opened the camera/mic, primed the filters
  and waited for its network addresses *before* the other phone could ring.

**What the big apps do, and what we took from them**
- Connect while it rings (WhatsApp, FaceTime): the connection is ready
  before Answer, and Answer only switches the sound and picture on. We
  already did this, but the camera wait above usually stopped it.
- Agree on the connection first and add the camera after, with no
  renegotiation (Mozilla's WebRTC guidance: transceivers and
  `replaceTrack`). **This is the fix:** both phones now build the
  connection with empty audio/video "slots" and fill them when the camera
  and mic are ready.
- A relay for both sides from the start (WhatsApp): kept as it was.
- Faster setup inside the browser itself (the IETF "WARP" draft, 6 → 2 round
  trips) needs browser changes, so no web app can use it yet.

**Results (best of two runs; the release gate re-measures every time)**

| | Live (23b) | 23e |
|---|---|---|
| Video: Answer → both hear | 2.0–2.7 s | 0.6–1.2 s |
| Video: Answer → both see | ~3 s+ | ~1.5–1.9 s |
| Voice: tap Call → other phone rings | ~0.95 s | 0.5–0.7 s |
| Video, slow camera: tap → rings | 3.8 s | 0.5 s |
| Caller: call recorded after tap | 1.25–2.1 s | 0.43–0.57 s |

- The caller opens the camera/mic **at the same time** as ringing only when
  permission is already granted; the first time (when the phone asks), it
  waits as before, so a "Block" still ends the call cleanly.
- If the mic fails after the other phone started ringing, the call ends
  and both phones are told (tested).
- **Mixed versions are safe:** 23e ↔ 23b voice and video, both directions,
  connect with sound and picture (tested), so a call between a phone that
  updated and one that hasn't works.
- What still takes time and cannot be removed from a web app: the
  database round trips that carry the call between phones, and waking a
  phone whose app is closed (push).

## 2. No fallback to an older version (app and console)
A slow server copy (a CDN edge that hasn't caught up, or a half-finished
upload) could put a phone back on an older version. Tested against the live
service worker, four ways it happened:
1. an older copy of a script replaced the newer one on the phone;
2. an older app page on the server was shown after the newer one;
3. when a new version installed while the server still gave an older page,
   that older page became the only copy on the phone;
4. the console showed an older console page.

Now **newest wins everywhere**: a copy from the server replaces what the
phone has only if it is not older (pages by their build stamp, other files
by the server's date). A newer version still arrives as before — tested.
Reloads are covered too.

**Rolling back:** because a phone never takes an older build, a rollback
must be released as a *new* build (the old code with a newer stamp).
